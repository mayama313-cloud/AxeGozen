# ミニオン v1 の教師データ収集

CPU戦またはオフラインで「ミニオン v1 の教師データを記録」を有効にして遊ぶ。
試合終了、リスタート、ロビーへ戻る際に、記録をIndexedDBへ保存する。
試合途中の「記録を保存してロビーへ」からも確認できる。
ブラウザーを閉じる前に試合を終了すること。進行中の記録はメモリ上にあり、強制終了からは復元できない。
1試合の記録上限は20分。上限以降も試合は続行できるが記録されない。

「記録・リプレイ」で試合と視点を選び、再生・一時停止・シークで確認する。
開始と終了を秒で指定して採用区間を追加する。取り消せば、その区間は書き出し対象から外れる。
初期状態では全区間が未採用。CPU区間の書き出しには別途チェックが必要。
区間は視点ごとに保存され、重なった区間がサンプルを重複させることはない。
記録JSONは全視点を含む原本。教師データJSONLは採用した視点・区間だけを含む。
JSONはダウンロード・再読み込みできる。保存領域が使えない場合も、ページ内に残った記録をJSONとして退避できる。
オンライン対戦の記録は未実装。

## 記録形式

原本のschemaは `axe-gozen-demonstration/1`。モデル名は `ミニオン v1`。
試合ID、作成時刻、ルール版、マップ・設定・キャラ定義、human/algorithmの出所、勝敗、採用区間を保存する。
`entries` はseqで全順序を持つ。時刻はゲームの30Hzのtickから計算する。

- `frame`: tick終了時の視点別観測。開始時刻0のフレームも記録する。
- `action`: 入力イベント、引数、入力直前の視点別観測、origin。
- `event`: その視点へ配信されたfx/hit/heal/kill。発生順も保持する。

観測は描画に使うものと同じ生成関数を通す。隠れた敵の座標や敵スキルのクールダウンは含めない。
マップ、キャラ情報、観測・演出・キルログの履歴を学習器へ渡すことで、最後に見た敵位置などを学習できる。
記録には画像・カメラ・マウスの連続軌跡は含めない。発動時の照準座標は入力として含む。
観測は構造化データであり、入力はゲームのワールド座標系にそろえている。
現状ゲームが敵HPなどを非表示中も配信するため、その情報は観測にも含む。視界ルールを変更したらルール版も更新する。

humanの入力は実際のゲーム入力処理に渡された要求を記録する。無効な要求も記録され、成功を意味しない。
CPUのスキル入力は同じ入力処理を通す。CPUの経路移動と通常攻撃は内部制御なので、対応するsteer/chaseをorigin=`derived`として記録する。
これは完全なCPU入力リプレイではない。CPUデータは既定で教師データから除外する。
リプレイは記録した観測と演出を再生する方式で、現在のゲームエンジンによる再シミュレーションではない。

## 教師データJSONL

先頭行はmanifestで、設定・出所・区間・試合IDのsplitKeyを含む。
以降は `axe-gozen-imitation/1` のサンプル。各行は直前のフレームから次のフレームまでの1区間。
`observation`、`actions`（各入力直前の観測付き）、`events`、`nextObservation`、dt、terminal、truncated、winnerを保存する。
同時刻の入力と演出もseqで発生順を復元できる。採用区間の切れ目はsequenceStart/sequenceEndで示し、途中終了はtruncatedとする。
入力のない区間もactions=[]で保存する。キー入力や自動攻撃の持続は自分のinputsと時系列から判断する。
区間境界をまたぐサンプルは採用しない。後続区間へ採用する場合も必要な過去履歴は学習器側で原本から与える。
勝敗やダメージ等を保存するが報酬値は決めていない。将来の強化学習ではこの結果から別途報酬を設計する。
学習・検証・評価はフレーム単位のランダム分割を避け、試合ID単位で分ける。

エンジンは `createMatch(solo, cpu, { trace })` により画面なしでも同形式を収集できる。
ゲーム挙動を変更した場合はinitのrulesVersionを更新し、異なるルールのデータが混ざらないようにする。

## 保存したデータで模倣学習を試す

原本を `datas/replays/*.json`、教師データを `datas/teachers/*.jsonl` に置く。
Node.jsとPythonが必要。Python側は `python -m pip install -r scripts/requirements-minion.txt` で依存関係を用意する。

```powershell
node scripts/minion-v1.js check
node scripts/minion-v1.js train --epochs 30
node scripts/minion-v1.js smoke
```

`train` は原本との整合性検査、学習用データの準備、Python/PyTorchでの学習、モデル保存、JavaScript推論の照合、60秒のゲーム内動作確認を順に実行する。
Git LFS管理のファイルを取得した後は、実体が作業フォルダーに展開されていることを確認する。
`version https://git-lfs.github.com/spec/v1`で始まる小さなファイルは、JSONではなくLFSの参照ファイル。
ローカルの実体は `git lfs checkout "datas/teachers/*.jsonl" "datas/replays/*.json"` で展開できる。
実体がローカルにない場合は `git lfs pull` で取得する。読み込み時にもLFS参照を検出し、対象パスと復元コマンドを表示する。
`--python`、`--teachers`、`--replays`、`--output` で実行ファイルや入出力先を変更できる。
同じ試合・視点・時刻を複数のJSONLから読み込むと、重複学習を避けるため停止する。
ルール版が混在する場合も停止する。CPU由来の教師データは既定で除外し、明示的に使う場合だけ `--include-cpu` を付ける。

出力先は `datas/models/minion-v1/`。

- `audit.json`: 原本と教師データの件数・出所・SHA-256。
- `model.json`: ブラウザー/Node.js共通の学習済み重み。
- `training.json`: 学習設定・損失・診断値と制限事項。
- `parity.json`: PythonとJavaScriptの推論照合用データ。
- `smoke.json`: 保存モデルを読み込み直してゲームを60秒動かした結果。
- `prepared.json`: 再現用の中間データ。Git管理対象外。

ロビーの「学習モデルを読み込む」で `model.json` を選ぶと、CPUの操作が「ミニオン v1」になる。
「CPU対戦」を開始し、対応キャラのCPUと対戦する。アルゴリズムへ戻す場合は「CPUの操作」を切り替える。
モデルファイルはページを読み直すたびに指定する。学習に登場しなかったキャラはCPUとして選べない。
学習モデルの操作も記録する場合、source=`model`として人間・アルゴリズムと区別する。

最初のモデルは動作確認用の小さなMLP。観測、マップ、設定、キャラ定義の全フィールドを1024次元へハッシュ圧縮するため、情報の衝突・損失がある。
座標と陣営を自分基準へ変換する。直近に見た敵の位置と、直近3秒・最大32件の演出の履歴を明示的に特徴へ追加する。
長期の記憶をニューラルネット自体が学習する構成や、生の画面・マウス軌跡を学ぶ構成にはしていない。
学習時はおおむね10Hzに間引き、スキル等の要求があった区間は残す。同区間に複数操作があればスキル等を優先して1操作にする。
クールダウン等で実行不能な要求は除外し、未入力時は保持中のキー入力またはnoopを教師にする。
推論は約10Hzで1操作を選ぶ。合法な操作のモデル確率から温度0.7・固定seedのサンプリングを行う。
学習例がゼロの操作は選ばない。経路探索やファーム判断を既存CPUから借りる救済処理は入れず、人間と同じ入力処理を通す。

1試合だけの場合、前半約80%を学習、後半約20%を診断とし、境界に3秒の空白を入れる。
これは同じ試合内での診断であり、別試合での評価・対戦の強さを示さない。移動が多いデータでは操作一致率だけが高くなるため、クラス別平均再現率も記録する。
複数試合がある場合は試合ID単位で分ける。正確な評価には別途、未学習の相手・試合条件での対戦が必要。

## 強化学習（PPO）

既存の模倣モデルを初期値にし、実際のゲームエンジンとの対戦結果から、操作選択と照準座標の両方を更新する。
模倣用の原本・教師データはこの処理では読み直さない。追加した実演を初期値に反映したい場合は、先に模倣学習を実行する。

```powershell
# 初回。模倣モデルは上書きせず、別フォルダーへ保存する。
node scripts/minion-v1.js rl --updates 100

# 長めの学習。試合の制限時間も延ばす。
node scripts/minion-v1.js rl --updates 1000 --max-seconds 600

# 強化学習モデルから継続。入力モデルとは別の出力先を指定する。
node scripts/minion-v1.js rl --model datas/models/minion-v1-rl/latest-model.json --reference-model datas/models/minion-v1/model.json --output datas/models/minion-v1-rl-next --updates 1000 --max-seconds 600

# Node.jsがPATHにない環境での例
& "$env:TEMP\axegozen-node-runtime\node.exe" scripts/minion-v1.js rl --updates 100
```

依存関係は模倣学習と同じ。学習器はPython/PyTorch、シミュレーターと共通の観測・操作変換はNode.jsで実行する。
CPUで動作する。現在の実装は複数環境を1つのNode.jsプロセス内で順に進め、Python側でバッチ更新する。

主なオプション:

| オプション | 既定値 | 意味 |
|---|---:|---|
| `--model` | `datas/models/minion-v1/model.json` | 初期モデル。対応キャラだけを訓練する |
| `--reference-model` | 初期モデル | 忘却を抑える参照モデル。継続時に元の模倣モデルを指定できる |
| `--train-base` | 無効 | 防衛用追加部分に加え、元のactor全体も更新する。既存動作との一致を維持する制約を外す |
| `--output` | `datas/models/minion-v1-rl` | 保存先。初期モデルと同じ場所は拒否する |
| `--updates` | 100 | PPOの更新回数 |
| `--steps` | 128 | 各更新で環境ごとに集める操作数 |
| `--envs` | 4 | 環境数 |
| `--max-seconds` | 120 | 1エピソードのゲーム内制限時間 |
| `--retreat-fraction` | 0.25 | 低HP・敵陣・近くに敵がいる状態から始める割合 |
| `--farm-fraction` | 0.2 | 自陣の小型キャンプ付近から始める割合 |
| `--defense-fraction` | 0.3 | 自陣タワーが攻撃されている状態から始める割合。練習割合の合計は1以下 |
| `--eval-episodes` | 16 | 学習前後の固定条件の診断回数 |
| `--eval-seconds` | 60 | 診断1回のゲーム内制限時間 |
| `--eval-every` | 25 | 何更新ごとに候補モデルを比較するか |
| `--seed` | 17 | 環境・探索・学習の乱数seed |

たとえば100更新×128操作×4環境は51,200操作。操作は約10Hzで、1操作ごとに物理演算を3tick進める。
対戦相手は既存アルゴリズムCPUで、キャラは全5種から選ぶ。訓練側は観測から選んだ入力を人間と同じ検証処理に渡す。
訓練側に既存CPUの経路探索や自動撤退を適用する処理はない。
通常試合のほか、敵陣でHP20〜40%から始める練習を混ぜる。通常の撤退練習に加え、さらに敵が近い難しい撤退練習も含む。
小型キャンプ付近から始めるファーム練習も混ぜる。実際のゲームでモンスターが出現した後に開始位置を変え、観測・攻撃・移動は通常の入力で行う。制限時間は開始位置の設定後から数える。
防衛練習では、AlexまたはMiraが自陣の前方タワーを攻撃する。敵は通常のchaseで攻撃し、CPUが迎撃して敵HPが40%未満になると通常のmoveで退く。敵のHP・領域ダメージ・タワーの攻撃は変更しない。
迎撃による20以上のダメージに貢献し、敵を撃破するか攻撃範囲外へ退かせ、タワーが生存すれば防衛成功。敵の自然死・タワーだけの撃破は成功にしない。課題は成功・敵や自身の死亡・タワー破壊・18秒経過で終了する。
防衛練習中、HPが十分あり、見える攻撃者がいる観測には、その敵へのchaseを短い模範操作として補助損失に加える。入力の種類と照準を学ぶ訓練専用の教師で、実行時に行動を上書きするルールではない。危険時の判断は強化学習で扱う。
撤退練習は、自陣でHP65%以上に回復できた場合または最初の死亡で終了する。死亡後の復活待ちや健康な状態で残り時間を消費せず、次の撤退判断を練習する。
低HPからの練習は訓練時だけの開始条件で、対戦中の行動を固定するルールではない。

報酬は勝利+20・敗北-20、敵タワー破壊+3・自陣タワー破壊-3、敵キャラ撃破+1.5・自身の死亡-2.5。
与ダメージ・被ダメージ・敵領域のダメージ・エネルギー獲得・経過時間にも小さな報酬を付ける。
エネルギー獲得は1につき+0.08。自陣の見えている小型モンスターへの接近・HP減少をpotentialに加え、攻撃と回復の往復だけでは報酬を稼げない差分方式でファームの進捗を伝える。
Qが実際に発動しても射程付近に見える敵がいない場合は-0.06、ゲームに拒否されたQ・着地指定は-0.02。直近2秒に目撃した敵へのブッシュ内攻撃は空振り扱いにしない。召喚・移動・防御スキルはこの空振り判定の対象外。
これは訓練の報酬であり、対戦時にQや空振りを禁止するルールではない。`attackAttempts`・`emptyAttacks`・`rejectedAttacks`も診断に記録する。
自陣タワーは破壊前から被ダメージ1につき-0.012。自陣タワー付近の攻撃者への迎撃ダメージは追加+0.006、防衛課題の成功は+3。
プレイヤーへの与ダメージ・撃破報酬は、CPU自身またはその召喚ミニオンの攻撃だけに付ける。領域や味方タワーのダメージ・撃破をCPU自身の成果として扱わない。
撤退については、HPと見えている危険度から計算した非負のpotentialの差 `gamma * Phi(next) - Phi(current)` を使う。
通常試合では回復ごとのボーナスを付けない。撤退練習では自陣への生還・回復を課題達成として+3にし、そのエピソードを終了する。
課題達成は試合の勝利とは区別する。自傷と回復を繰り返すだけの正の報酬サイクルを避ける。
potentialsや報酬の設定値は `rl-training.json` に保存する。対戦の強さを保証する設計ではなく、今後の診断で調整する。

PPOは離散操作・8方向と停止・追跡の維持/解除・連続照準の同時確率を使い、GAEとclipped objectiveで更新する。
移動方向は訓練・ブラウザー共通のカテゴリ分布から選ぶ。狭い連続ノイズだけで撤退方向の探索ができなくなる問題を避ける。
元のモデルへのKL制約を付け、健康な状態ほど参照モデルを強めに維持する。低HP時の撤退を覚えた結果、健康でもひたすら逃げる状態になることを抑える学習上の正則化。
行動をHP条件で切り替える実行時ルールは設けない。訓練時には照準の探索ノイズを入れるが、ブラウザーでは予測した平均照準を使う。
criticにはactorと独立した中間層を使う。価値推定の大きな誤差で、actorの模倣済みの中間表現を直接書き換えない。
gamma=0.997、GAE lambda=0.99とし、撤退して回復するまでの数秒以上の結果を反映しやすくする。
強化学習では、実演が0件だったリコール等も、ゲームの条件を満たす場合に探索できる。
時間切れは勝敗と区別し、criticで最終状態をbootstrapする。次の試合へGAEを持ち越さない。
途中経過は更新ごとに保存する。継続時にはactor・critic・探索分散を読み込むが、optimizerは作り直す。

出力:

- `model.json`: 候補選択用の別seedで比較して採用した推奨モデル。ロビーの「学習モデルを読み込む」で指定できる。
- `latest-model.json`: 最後の更新のモデル。継続学習にはこちらを指定する。
- `initial-model.json`: 学習開始時のモデルのコピー。実行中に入力ファイルが更新されても、比較・訓練の初期値は変わらない。
- `warm-start-model.json`: 観測・移動表現を更新した直後、まだ強化学習で更新していないモデル。
- `imitation-reference.json`: KL制約の参照に使う元モデルのコピー。
- `rl-training.json`: 報酬、学習履歴、実際の重みの変化量、学習前後の診断と各エピソードの結果。
- `parity.json` / `smoke.json`: PythonとJavaScriptの推論照合、および通常ゲーム内の動作確認。

診断はキャラごとに通常開始・撤退・難しい撤退・防衛を割り当て、未使用の同じseed・キャラ・開始条件で学習前後を比べる。全組合せを含めるには最低4×対応キャラ数のエピソードを指定する。
防衛は`defenseAttempts`・`defenseStops`・`defenseInterventions`・`defenseTowerDamage`を保存する。敵が自滅しただけの結果と、CPUが迎撃に向かった結果を分けて比較する。
撤退の指標は「HP40%以下を経験し、最初の死亡前に自陣でHP65%以上まで回復できたか」。これは撤退行動を完全に分類する指標ではない。
死亡数・勝敗・タイムアウト・与被ダメージ・エネルギーに加え、低HP時の追跡命令数、自陣へ近づく移動と離れる移動の数も保存する。
候補選択用seedと最終診断用seedは別にする。基準は入力した初期モデルとし、通常開始で得たエネルギーが85%未満、または撤退成功率が12.5ポイントを超えて下がる候補は、勝利数が増えた場合を除いて採用しない。
この基準を通過した候補を勝敗差、撤退成功率・防衛成功率・ファーム量・空振り率の複合スコア、死亡率、報酬の順で比較し、更新の最後という理由だけでは採用しない。
元モデル・表現変更直後のモデルも比較対象。改善しなかった場合には元モデルを推奨として残し、最新の更新はlatest-model.jsonへ別保存する。
少ない試行での数値の上下は改善の証明にならない。正常な攻勢やファームが維持されているかも実際の対戦で確認する。
初期モデルと現在のゲーム設定が異なる場合、訓練・診断には現在のゲーム設定を使い、保存モデルのinitにもその設定を記録する。

### 改善版の観測と操作

新しい防衛モデルには `featureVersion=minion-defense-alarm/6` を保存する。既存のv2・v3・v4・v5も従来どおり読み込める。
既存1024次元のうち末尾32次元を、HP割合、見えている敵のHP、敵と自陣への方向・距離、敵領域への侵入、追跡中か、キー入力、スキルCD等の明示的な特徴にする。
v3はさらにその直前16次元に、見えている自陣の小型モンスターの相対座標・HP・射程、エネルギーの相対座標、移動先・現在の攻撃対象の相対座標を保存する。敵の非公開座標や、見えていないモンスターの位置は追加しない。
v4はその直前16次元に、脅威のある自陣タワーのHP・相対座標・最近の被害、見える攻撃者のHP・相対座標・距離、残存タワー数とHPを保存する。タワー被害の履歴は公開HPの変化から取り、ブッシュで見えない攻撃者の座標は加えない。
v4の試験では防衛を学ぶ一方、元の撤退判断を忘れる回帰があったため、v5以降は元の方策を固定する。v3の1024入力と重みをそのまま保存し、末尾に防衛用16入力を追加する（計1040）。`defenseAdapter=frozen-base/1`として元のactorの入力重み・バイアス・各出力ヘッドを固定し、追加16入力から出力への補正重み`weights.defenseW`だけを学ぶ。criticは別に更新する。防衛補正の学習率は0.001、criticと探索分散は0.0001。
v5は付近の敵にも反応してファームを中断したため、v6では公開タワーHPの減少を見てから3秒間の被害履歴を合図とする。合図がない場合は追加16入力をすべて0にし、同じ観測・履歴に対する出力を元のv3と一致させる。被害が続けば合図も継続する。防衛中の移動・攻撃対象・スキルは引き続き学習モデルが選び、固定の迎撃入力を挿入しない。
初期値にはv3ファームモデルまたは既存v5・v6を推奨する。入力スロットを置き換えていたv4からの移行は拒否する。例：

```powershell
node scripts/minion-v1.js rl --model datas/models/minion-v1-rl-v3-farm/model.json --output datas/models/minion-v1-rl-v6-next --updates 100
```
新しい特徴に対応する入力重みは移行時に0から学び直す。旧モデルの観測・操作の解釈は変更しない。
移動方向の追加ヘッドには `weights.directionW/directionB` を保存し、元の連続移動予測を弱い初期の優先方向として使う。
`movementOrder=stop-clears-chase/1` のモデルは、8方向の移動では現在の攻撃対象を維持し、モデルが停止方向を選んだ場合に現在位置へのmoveで追跡を解除してからsteerを送る。
これにより、モンスターへの攻撃を移動のたびに切らずに、モデル自身が追跡の中止も選べる。
この指定がない初期のtactical/2試験モデルは、手動移動ごとに以前の追跡を解除する方式で再生する。新しい学習では通常戦闘を維持する指定を保存する。
現在の新規学習では `movementOrder=learned-chase-order/1` と `weights.orderW/orderB` を保存する。
方向を選ぶのと同時に、以前の追跡を維持するか解除するかを追加ヘッドで学ぶ。解除を選んだときだけ現在位置へのmoveを先に送る。
停止方向は追跡も解除する。HPによる固定ルールで切り替えず、通常の攻撃対象を維持する移動と、追跡を断ち切って逃げる移動の両方を選べる。
どちらも人間が使える既存入力であり、ゲームのスタン・クールダウン・衝突の条件を通る。HP条件で自動撤退させる処理ではない。
`controlProtocol=release-before-chase/1` は、攻撃対象を選ぶ前にsteerのゼロ入力を送り、前の方向キーを離す。
これにより、chaseを選んだ後も前の移動キー入力が残って別方向へ歩くことを防ぐ。人間のキー解放と同じ入力処理を通す。
`aimProtocol=release-invalid-leap/1` は、無効な着地点へのジャンプ指定を照準解除に変換する。人間用UIで無効な位置のままキーを離した場合と同じで、無効な指定を照準状態のまま繰り返すことを防ぐ。着地可否はゲーム共通のvalidLandingで判定し、隠れた敵の情報は使わない。
方向ヘッドがない旧モデルは従来の連続移動のまま動作する。

PPOの元論文: [Proximal Policy Optimization Algorithms](https://arxiv.org/abs/1707.06347)。

### 目的選択 v7：無駄な操作と中央トナカイ

`datas/models/minion-v1-v7-objectives/model.json` は、v6のactor・防衛用重みを保持したまま、別の小さな目的選択モデルを追加する。目的は元のモデルへの委譲、小型モンスター、中央の大型トナカイ、エネルギー、最初の小型キャンプへの移動。
24特徴・中間32ユニットのMLPで各目的の価値を評価し、最も高い目的を選ぶ。HP、移動時間、報酬、目撃したHP減少速度、到着時の推定HP、一撃で取れるか、敵との競合、現在の目標、足止めを観測する。非表示のモンスターの現在HPや座標は取得しない。

この追加部分はPPOではなく、狭い判断だけを扱う合成の模範データによる模倣学習。初期データは6,000状況で、状況単位で4,800訓練・1,200検証に分ける。元の不完全なCPUをそのまま教師にはせず、「到着できる低HPの大型を優先」「到着前に倒されるなら追わない」「低HP・リコール・タワー被害中は元モデルへ委譲」を教える。模範スコアは実行時の選択には使わない。
取得優先の判断には大型HP40%以下の特徴も与える。敵が近い大型の競り合いでは、攻撃用Q/Cは原則として致死ダメージを出せるまで温存する。小型を選んだ場合でも、大型の状況は毎回評価し直す。

目的への経路探索と攻撃操作はアルゴリズムで実行する。選んだ目的を通常のmove/chaseで追い、同じ目標への移動指示を毎回リセットしない。Q/Cは射程内の実在する対象へ向ける。移動経路は公開マップの障害物・タワー・敵安全地帯だけを使い、隠れた敵は経路計算に使わない。すべて通常のプレイヤー入力を通る。
元モデルへ戻すときは、目的選択層が所有していた古い追跡を解除してから操作を渡す。目的選択の履歴は元actorのハッシュ観測に混ぜない。

```powershell
# 目的選択層を学習。既存actorの重みは更新しない。
node scripts/minion-objectives.js train --model datas/models/minion-v1-rl-v6-defense/model.json --output datas/models/minion-v1-v7-objectives --epochs 100

# 同じ条件で旧版と比較する。標準48エピソード、各通常試合60秒。
node scripts/minion-objectives.js evaluate --model datas/models/minion-v1-v7-objectives/model.json --reference datas/models/minion-v1-rl-v6-defense/model.json
```

Node.jsがPATHにない場合は、`node`の代わりに`& "$env:TEMP\axegozen-node-runtime\node.exe"`を使う。
`objective-training.json`は模倣精度、`objective-parity.json`はPython/JavaScriptの目的評価の照合、`comparison.json`はゲーム内比較。生成元データの`objective-prepared.json`は再生成できるためGit管理対象外。
追加の診断は`large-finish`と`large-contest`。実際のHPを持つ大型に通常の入力で攻撃し、敵とのラストヒット競争も含める。成功は実際の撃破イベントと報酬の獲得で判定し、目的を選んだだけでは成功にしない。
`unproductiveSeconds`は、生存・行動可能・回復待ちや初回キャンプ待ちでないのに、移動・有効な攻撃・射程内の攻撃対象がない時間。空振り入力数・大型取得数・競り合いでの取得数も比較する。合成データでの精度は対人勝率ではない。

```powershell

```

## Webの自動対戦・勝率計測

ロビーで「自動対戦・勝率計測」を選び、試合開始を押す。設定画面でA・BそれぞれにアルゴリズムまたはJSONモデルとキャラクターを指定し、先取本数を決めて「自動対戦を開始」。モデル同士、モデル対アルゴリズム、アルゴリズム同士に対応する。モデルの対応外キャラは選択肢から除外する。

- 描画オフ：Web Worker内で描画なしの高速処理を行う。
- 描画オン：同じ処理を1・4・16・64倍で観戦する。A/Bの視点を切り替えられ、対戦中でも描画のオン・オフを変更できる。
- 各試合はタワー5本の全破壊で勝敗を確定する。時間上限の既定値は0（無制限）で、60秒では打ち切らない。
- 上限を設定した場合と手動で引き分けにした場合は、引き分けとして別集計する。先取本数を増やさず、勝率の分母にも入れない。
- 一時停止・再開に対応する。中止時の未決着試合も勝敗に入れない。指定した本数を片方が先取すると自動停止する。
- 初期陣営の交代は標準でオン。A/Bの識別は陣営を入れ替えても保持し、ゲーム内の先手・陣営差を交互に受ける。

勝率は`勝数 / 決着した試合数`。まだ決着がない場合は0%ではなく「—」を表示する。設定した先取シリーズ内での勝率であり、少数試合の結果だけで一般的な強さを断定しない。
結果表には勝者、決着までの時間、初期陣営、タワー残数、獲得エネルギーを表示する。「結果JSONを保存」で全試合、モデル名・ファイル名・可能な環境ではSHA-256、キャラ、乱数シード、ゲーム設定、途中中止の状態を保存できる。表示は直近100試合、JSONには全試合を含む。

モデルごとに独立したメモリーと乱数列を持たせ、毎試合リセットする。各モデルが受け取る観測はその陣営の通常の視界に制限する。描画速度は物理演算のtickや乱数の進め方を変更しない。観戦中のプレイヤー操作は受け付けず、比較対戦を通常の教師データ記録に自動混入させない。
この処理は開いているブラウザー内で実行する。ページを閉じた後も動くサーバージョブではない。モデルファイルはローカルから読み込み、Web Workerへ渡す。

## チーム編成（各1〜5人、非対称編成）

CPU対戦・オフライン・オンラインは、ロビーの「チーム編成・オンラインの部屋」を開き「チーム編成を使う」をオンにする。A・Bの人数を独立して1〜5人に設定し、CPUごとにアルゴリズム／モデルファイルとキャラクターを指定する。人数をそろえる必要はなく、1対5・2対3などに対応する。オフラインとCPU対戦はAの1人目が自分で、他の席はCPU。編成を使わない場合は従来の練習・1対1の動作を維持する。

オンラインの編成あり対戦は部屋方式。作成者はAの最初の人間席に入り、他の人間は部屋コードと参加チームを指定して空席に参加する。ホストは対戦前に人間用の席やCPUを追加・削除でき、空席の種類とCPUキャラ・モデルも変更できる。両チーム1〜5人、合計最大10人の人間／CPUを混在できる。参加中の人間の席はホストでも削除・CPU化できない。
全ての人間が席に入り、自分のキャラを指定して準備完了すると試合開始。編成を変更したら人間の準備を解除する。オンラインCPUのモデルはサーバーへ送信して実行し、他の参加者へはモデル名・対応キャラ・ハッシュなどの情報だけを送る。人間が試合中に切断した場合は同じ席をアルゴリズムCPUへ引き継ぎ、残った参加者は続行できる。

自動対戦もA・B各1〜5人。メンバーごとに別のモデルやキャラを使い、チーム単位で先取本数・勝率・タワー・合計エネルギーを集計する。陣営交代では編成全体を入れ替え、観戦は任意のメンバーの視点を選べる。JSONには全メンバーのモデル情報と個人成績を含む。旧`entries: [A, B]`の1対1設定も読み込め、新しい編成は`teams: [[member, ...], [member, ...]]`で表す。

エンジンの`slot`は陣営（0/1）のまま保持し、`member`と固有IDで各キャラクターを区別する。各プレイヤーに別々のHP・CD・復活・入力・ポリシーを持たせ、タワー5本と領域・獲得エネルギーによる領域拡大はチーム共有。攻撃は敵チームだけに当たり、味方を敵の記憶や競合対象に入れない。視界は従来の陣営判定を使い、モデルには本人の入力と陣営から見える観測だけを渡す。旧1対1モデルの重みは更新しないため、多人数戦での強さは別途評価する。
複数人の記録・リプレイも視点別に保持し、選択欄にチーム・メンバー番号を表示する。

## コンペティション（シリーズ／スイスステージ）

ロビーの「コンペティション」から開き、大会形式を選ぶ。既存の「自動対戦・勝率計測」も同じ画面へシリーズ形式で入る。シリーズは2チームの先取戦。スイスステージは2〜16チームを登録し、各チームに1〜5人のアルゴリズム／学習モデルCPUを編成する。各チームの人数は独立。モデルはメンバーごとにJSONを読み込み、対応キャラから選ぶ。

スイスのラウンド数は1〜参加チーム数−1。初期シード順は指定した乱数シードから再現可能に生成し、以降は順位順に近い勝ち点同士を優先して組む。全体の組み合わせを探索して再戦を避け、成立しない場合は再戦を許可して結果欄に示す。奇数チームの不戦勝は、まず不戦勝回数が少なく、次に勝ち点が低いチームを優先する。各ラウンドの全対戦が終わってから次の組み合わせを決め、試合は順番に実行する。

各組み合わせは設定した本数の先取戦。ただしスイスでは引き分けによる無限再試合を防ぐため、最大ゲーム数を「2×先取本数−1」とする。上限ではゲーム勝数が多い側の勝利、同じなら対戦全体を引き分けとする。通常のシリーズにはこのゲーム数上限を設けない。時間上限0は無制限で、タワーを破壊して決着するまで実行する。

勝利・不戦勝1点、引き分け0.5点、敗北0点。順位は勝ち点、対戦相手の最終勝ち点の合計（Buchholz、不戦勝を除く）、ゲーム勝数−敗数、初期シード順で決定する。不戦勝は勝敗欄と分けて集計し、ゲーム勝数には加えない。順位表は進行中の暫定順位で、全ラウンド終了時に確定する。上位抜けのプレーオフは含まない。

Web Workerで裏の高速処理と描画を切り替え、現在の組み合わせの任意メンバーを観戦できる。一時停止・再開・現在のゲームを手動引き分け・中止に対応。中止時の未決着の組み合わせには勝ち点を与えない。JSONには大会シード、ラウンド、全参加チームのモデル情報、全組み合わせと勝ち点・順位、各ゲームの成績・シードを保存する。描画のスコア・勝率・タワーは現在の組み合わせについての表示。ページを閉じると処理は終了する。

## 目的選択 v8：攻勢・侵入・スティール

`datas/models/minion-v1-v8-offense/model.json` を画面から読み込む。v7の候補が「自陣の小型／大型／エネルギー／初期キャンプ」に限られていたため、v8では見えている敵陣の小型と生存中の敵タワーを追加した。旧v7のモデル・24特徴の仕様は保持し、v8は`minion-objectives/2`、37特徴・中間64ユニットの目的選択層を使う。actor・防衛の既存重みは変更しない。

追加観測は、敵領域にいるか、攻撃と帰路にかかる領域／タワーの推定HP損失、目標付近の敵圧力・味方支援、敵死亡・遠方・低HP、敵を見失っているか、到着時のHPから見たスティール可能性。敵が不明なことを安全と扱わず、深い侵入のコストも評価する。推定は簡略化したもので、未来の敵行動や非表示モンスターのHPは取得しない。低HP・リコール中・直近の自軍タワー被害では攻勢を選ばず、既存actorに戻す。

12,000の合成状況で目的の価値を模倣学習した。状況を乱数で訓練9,679／検証2,321に分け、150 epochで目的一致96.0%、安全状況1,057件で100%、大型優先397件で99.2%。タワー優先171件で83.0%であり、攻め時の判断にはまだ誤りが残る。教師スコアは実行時には使用せず、学習済みMLPで選択する。移動・経路探索・攻撃実行は既存の通常入力を使う。競合する小型でもQ/Cをラストヒットまで温存し、タワー攻撃ではアレックスの召喚も使用する。

固定した4キャラの実戦診断（同じ配置・通常入力）の結果：

| 指標 | v7 | v8 |
| --- | --- | --- |
| 敵不在のタワーへの攻撃開始 | 0/4 | 4/4 |
| 敵陣キャンプの取得 | 0/4 | 4/4 |
| 敵と競合する小型のスティール | 2/4 | 3/4 |
| 防衛成功 | 4/4 | 4/4 |
| 中央大型の取得（通常＋競合） | 7/8 | 7/8 |
| 低HPから回復する診断 | 1/4 | 1/4 |
| 通常対戦 vs アルゴリズム（600秒上限、全試合決着） | 0勝4敗 | 0勝4敗 |

これは少数の固定診断で、一般的な勝率ではない。攻撃機会を使う行動は確認できたが、通常対戦の勝利増加は確認できていない。低HP時の既存actorの回復性能も改善していない。`offense-comparison.json`に配置条件に対応する診断結果・試合別成績を保存する。

```powershell
# v7を残して攻勢用の目的選択層を学習
node scripts/minion-objectives.js train --offense --python D:\git\python\python.exe --epochs 150

# v7とv8を固定診断・最後までの通常対戦で比較
node scripts/evaluate-minion-offense.js
```

Node.jsがPATHにない場合は`node`を`& "$env:TEMP\axegozen-node-runtime\node.exe"`に置き換える。CPU戦・チーム編成・コンペティションではv8の`model.json`を指定する。自動で既存v7を置き換える処理は行わない。
